## What difficulties do I see

**1. The measurement harness is noisy enough to undermine the ratio gates it's built to enforce.** Most bake-offs are single-shot (`reps=1`) on a shared, unisolated dev box. The clearest proof: the *llama.cpp reference number itself*, for the identical tinyllama Q4_K_M CPU config, was 46.0 tg on 2026-09-12 19:34 (session 79) and 5.04 tg on 2026-09-13 03:27 (session 80), roughly 13 hours apart. That's a 9x swing in the denominator of every "Juno/llama" ratio in the table, on a run where nothing about Juno changed. Separately, Juno's own GPU tinyllama tg wanders 25.6 to 39.3 across nominally unrelated "default path" checks, a band wide enough to hide a real regression or manufacture a false one. None of the P0/P1 ratios (0.15x, 0.5x, 1.3x) can be trusted to the precision they're quoted at until this is fixed.

**2. The default path never exercises the configuration that actually solves the project's headline problem.** `--mmq` and `--gpu-layers` both default to off. Mistral-7B on this 8GB card sits at 0.42 to 0.49 tg across sessions 72, 73, 75, 76, and 77's default-path checks, worse than Juno's *own* CPU numbers for smaller models. The one time the team ran `--mmq on --gpu-layers auto` (session 78's dedicated bake-off), the same model hit 15.3 tg, roughly 30x better. So the "regression gate" that's supposed to protect this model is, most sessions, measuring a configuration nobody would actually run in production.

**3. `juno-documentation` (the tree README.md points to as `ml.cab/juno-documentation`) is stale for the entire review window.** `part11/02-changelog.md` was updated once, at commit `3835bd3`, right at the start of this window, then never again, despite CLAUDE.md rule 5 requiring it alongside `CHANGELOG.md` every session. Of 62 files in that tree, only 3 have moved since Aug 24-29. `CHANGELOG.md` and `docs/agent-arch.txt`, by contrast, are current through session 82, so the team clearly can keep docs in sync; it just isn't propagating to the public tree.

**4. `run.bat` is missing four flags that `run.sh` has**: `--gpu-layers`, `--parallel`, `--batch-window-ms`, `--prefill-batch`. All four came from the unlabeled pre-69 block. Every later session's flags (`--mmq`, `--schedule`, `--kv-page-size`, `--cache-type-k/v`, `--embeddings`, `--hf`, `--grammar-file`, `--tool`-related) made it into both scripts. Windows users currently cannot reach GPU-layer offload or batching from the launcher at all.

**5. `JUNO_*` tunables resolve three different ways.** `MmqOptions`/`GpuLayerOffload` read `System.getProperty` only. `ServeBatchOptions` and the grammar/schema file options read `System.getenv` only. `CacheTypeOptions`/`KvPageSizeOptions`/`ServeScheduleOptions` check both. A user who does `export JUNO_MMQ=on` gets silently ignored with no error, which is the worst kind of misconfiguration for a performance flag.

**6. `hs_err_pid8816.log` is tracked in git**, committed in `8b78382` (finish LoRA play MMQ), timestamped about 15 minutes before that commit. It's a `ShouldNotReachHere()` fault in the JFR sampler thread while `--jfr`, `--mmq on`, and `--lora-play` were all active together, plausibly a JFR/Panama-FFI thread-suspend interaction during a native downcall. It's never mentioned or explained in any CHANGELOG entry, and the entire perf methodology depends on JFR being trustworthy under exactly this kind of load.

**7. P0, the phase the team's own roadmap says gates all "peer" claims, is still open, and nothing after session 78 pushed on it.** Their own historical note: pre-window, Juno GPU decode was 0.17-0.22x llama.cpp with `juno.MatVec` at 93-96% of decode time. Session 78 got Phi-3.5 to 0.33x (need 0.5x) via the Q8_1/dp4a kernel. Sessions 79-82 pivoted to API-surface features (grammar, tools, chat templates, embeddings), which their roadmap explicitly permits since those aren't P0-dependent, but it does mean the core single-stream decode gap has sat unattended for four sessions.

**8. Smaller, contained items**: an unreachable defensive branch in `ContinuousBatchEngine.runDecode` (a `maxTokens` guard that can't trigger given the current control flow, a sign of fast same-day iteration without a cleanup pass); non-atomic `closed` guards in `DeviceQ4KMatrix`/`ResidentQ4KWeight` (checked-then-set `boolean` rather than `AtomicBoolean.compareAndSet`, low risk today because LoRA fails closed under continuous scheduling, but a latent double-free if that constraint is relaxed); and `CHANGELOG.md` uses an em-dash as its literal session-header separator 252 times, directly against CLAUDE.md rule 10, with zero enforcement anywhere in the window.

## What we may do better to improve inference performance

**1. Fix the O(n²) history reconstruction in the decode hot path.** `ContinuousBatchEngine.runDecode` (and the static `GenerationLoop`, same pattern) rebuilds `historyArr` via `generated.stream().mapToInt(Integer::intValue).toArray()` on every single decode step, for every active slot, from a `List<Integer>`. That's a full boxed-list traversal plus array allocation per token per slot, compounding over a generation. This sits directly on top of the gather-tax work the team already fought hard to shrink (10.7% to 4.6%) and is worth profiling before concluding the continuous-batching 0.86x-vs-static number is a structural, unfixable tradeoff; part of it may be avoidable JVM churn. Swap to a primitive growable `int[]` buffer maintained incrementally.

**2. Make the VRAM-fit path the thing that gets measured every session, not once.** Add a standing "tuned" lane (`--mmq on --gpu-layers auto`) to the regular regression sweep for Mistral-7B specifically, alongside the vanilla-default lane. Given the 30x gap between them, this is the single highest-leverage change to the *measurement* process, and arguably the flags should auto-enable when the loader detects a model won't fit resident in FP16 rather than requiring the user to know they exist.

**3. Push the Q8_1/dp4a kernel further before moving to a different lever.** Phi-3.5 is at 0.33x peer, needs 0.5x. Session 71's text framed the 1.3x target as needing a dedicated "tile Q4 kernel," but session 78's dp4a rewrite already cleared that bar (1.51x). The remaining gap to peer parity is more likely occupancy/tiling of the GEMV kernel itself (rows per thread block, coalescing across the Q4_K super-block layout) than the quantization scheme. Nsight Compute against the now-known 0.32ms p95 baseline would tell you directly rather than guessing.

**4. Stabilize the harness before trusting any more of these ratios.** Bump `REPS` above 1 for the standing bake-offs (the AWS `perf-lib.sh` harness already has this pattern, just isn't the one being used locally), and consider a rolling median for the llama.cpp reference number specifically, since that's the one that swung 9x with zero Juno code involved.

**5. Extend fused-kernel coverage past the QKV/gate-up projections.** MMQ's 1.51x on Phi-3.5 GEMV is real, but GEMV is roughly half of decode time by the team's own JFR breakdown; attention, softmax, and sampling make up the rest and haven't had the same treatment. That's the next biggest lever after closing the P0 gate itself.

## What I'd suggest overall

The core engineering here is solid. Fifty-seven new classes, judicious use of the "prefer new classes" rule with one well-justified exception (rewriting `Q4KMmqKernel`/`DeviceQ4KMatrix` in place for the Q8_1 kernel swap, since the public contract didn't change), sound concurrency design in `ContinuousBatchEngine` (single virtual-thread actor consuming a `PriorityBlockingQueue`, correctly sidesteps almost all the data races a naive concurrent scheduler would hit), and a genuinely disciplined habit of shipping behind default-off flags and writing "feature complete, gate unmet" in plain language instead of overclaiming. The problems I found are almost entirely in the glue layer, not the algorithms: measurement rigor, doc propagation, launcher parity, config-resolution consistency.

Given that, I'd prioritize in this order: fix the measurement noise first, since it's currently undermining confidence in every other number in this review; add the tuned-lane Mistral check second, since it's cheap and directly addresses the biggest real-world gap; then decide, explicitly, whether to resume the P0 kernel push or formally defer it, rather than let it drift by default while feature sessions continue. The documentation and `run.bat` gaps are low-risk to fix and worth a single cleanup session. I'd also suggest a lightweight "gate ledger," one line per open P0/P1 gate with current number, target, and date, refreshed in `docs/agent-arch.txt` each session, since right now reconstructing "what's actually still open" requires reading all 14 session entries plus the roadmap doc side by side, which is what I had to do to build this table.
