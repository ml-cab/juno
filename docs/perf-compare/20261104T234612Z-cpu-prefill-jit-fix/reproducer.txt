Fresh JVMs on this host (JDK 25.0.4.1, Xeon E5-1650 v2), CpuIntegerGemm alone at prefill width: per window, layers of
four Q4_K 2048x2048 matmuls and one Q6_K 2048x5632 matmul at 572 activation rows (synthetic weights from
CpuIntegerKernelsTestSupport). Bytes allocated per matmul call on all threads, and window time. "old" is 80ec949e's
CpuIntegerGemm; "first form" the change with the offset negated per row; "final" the change as committed for the gate.
Window 1 includes the interpreter and C1 before the kernels compile; the later windows are the compiled kernels.

1. No other vector shape first: never reproduced. Old kernel, 22-layer windows, window 2 at 1,261 bytes/call in all of:
   default flags (4 runs), -XX:-UseOnStackReplacement (2), the decode kernels run first (2), -XX:-TieredCompilation (2),
   -XX:PerMethodTrapLimit=0, -XX:PerBytecodeTrapLimit=0, without aggressive reboxing, -XX:-UseLoopPredicate,
   -XX:TypeProfileLevel=0. Blunt flags that do reproduce it but change C2 for every method: -XX:TypeProfileWidth=0
   (17.7 GB/call), -XX:LiveNodeCountInliningCutoff=4000 (299 MB/call).

   only: 1,261 bytes/call (two runs).

   old, 4 layers:    window 3: 11.0 s and 17.8 s, 8.5 and 14.9 GB/call (two runs)

   Other shapes first, then 128 bits: old, 22 layers, window 2: 134.4 s and 150.9 s, 14.5 and 15.3 GB/call.
